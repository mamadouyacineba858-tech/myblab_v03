## B. MISSION

### Problème à résoudre

Le déplacement d'un composant (`MOVE_COMPONENT`) constitue encore une mutation persistante exécutée par le chemin historique du canvas, alors qu'un Handler Core `MoveComponentHandler` existe déjà et que CF3 dispose désormais d'un canal de mutation production utilisé par `ADD_COMPONENT`, `ADD_WIRE` et `UPDATE_WIRE_WAYPOINTS`.

Le présent ticket formalise la migration **strictement contrôlée** de `MOVE_COMPONENT` vers :

```text
UI → CommandBus → ValidationEngine → MoveComponentHandler → HistoryService → Document
```

sans supprimer ni remplacer globalement l'infrastructure historique existante dans le cadre de ce ticket.

### Objectif

À l'issue du ticket, une session de déplacement utilisateur doit produire **une seule mutation persistante `MOVE_COMPONENT` au relâchement**, avec historisation dans la pile Undo/Redo existante, tout en conservant les garanties fonctionnelles actuelles du déplacement.

## C. AUTORITÉ ET FRONTIÈRES

1. Le présent ticket est un **contrat PMO d'exécution contrôlée**.
2. Les décisions architecturales déjà verrouillées par les ADR, rulings CSA et contrats CF3 applicables restent prioritaires.
3. Aucune décision nouvelle ne peut être inventée pendant l'implémentation.
4. Le périmètre est limité à `MOVE_COMPONENT`.
5. Ce ticket **n'autorise pas** la migration de `REMOVE_COMPONENT`, `UPDATE_COMPONENT`, `TOGGLE_LATCHING_BUTTON` ou d'une autre mutation.
6. Ce ticket ne supprime pas `HistoryManager`, `MoveCommand` ou les autres commandes legacy hors du chemin effectivement migré.
7. Aucun changement de Simulation, Arduino Bridge, Presentation visuelle hors déplacement, ou contrat des pins n'est autorisé sauf nécessité directe et démontrée pour satisfaire les critères de ce ticket.
8. Toute difficulté qui impose une nouvelle décision architecturale doit provoquer un arrêt et un rapport factuel au CSA.

## D. ÉTAT TECHNIQUE DE RÉFÉRENCE

Le dépôt contient déjà `MoveComponentHandler`, qui valide `componentId` et `position`, applique la nouvelle position dans le Document Core et fournit les données nécessaires à Undo/Redo via l'infrastructure `BaseCommandHandler` / History. Le Handler ne doit donc pas être réinventé sans preuve d'insuffisance du contrat existant.

Le hook `useCircuitState` dispose désormais d'un `documentApi` capable de produire un document Core via `ReactDocumentMapper.toCore()` et de réappliquer un document Core via `ReactDocumentMapper.toReact()`. Ce mécanisme constitue le pont documentaire déjà présent dans la branche `main`.

Le canal CF3 production actuellement enregistré dans le hook comprend explicitement :

- `ADD_COMPONENT` ;
- `ADD_WIRE` ;
- `UPDATE_WIRE_WAYPOINTS`.

`MOVE_COMPONENT` est volontairement absent de ce registre et constitue donc le périmètre de ce ticket.

L'infrastructure historique legacy du drag doit être inspectée avant modification afin de préserver son comportement utilisateur et de vérifier qu'aucune mutation concurrente ne subsiste après migration.

---

## E. CONTRAT D'EXÉCUTION

### E.1 Mutation canonique

Le déplacement doit utiliser une commande de forme :

```javascript
new Command("MOVE_COMPONENT", {
  componentId,
  position: { x, y }
})
```

Le nom et la forme exacte ne peuvent être modifiés que s'ils contredisent le Handler ou une convention Core déjà verrouillée. Aucune nouvelle forme concurrente ne doit être créée.

### E.2 Canal de mutation obligatoire

Le chemin persistant cible est :

```text
pointer drag
   ↓
aperçu local pendant le drag
   ↓
pointer up
   ↓
MOVE_COMPONENT Command
   ↓
CommandBus
   ↓
ValidationEngine
   ↓
MoveComponentHandler
   ↓
HistoryService
   ↓
Document API
```

Aucun `setComponents()` direct ne doit persister la position finale du composant en parallèle du dispatch `MOVE_COMPONENT`.

### E.3 Une mutation par session de déplacement

Le déplacement visuel pendant le drag peut rester réactif et local.

En revanche :

- aucune mutation persistante par pixel ;
- aucun dispatch `MOVE_COMPONENT` à chaque `pointermove` ;
- une seule commande au `pointerup`, uniquement si la position finale diffère réellement de la position initiale ;
- si aucune position n'a changé, aucune commande persistante ne doit être créée.

Le comportement de snap-to-grid existant doit être conservé si celui-ci fait partie du chemin actuel de déplacement.

## F. PÉRIMÈTRE TECHNIQUE

### F.1 Inspection obligatoire du drag actuel

Avant modification, identifier précisément :

- `startDrag` / équivalent ;
- mise à jour des positions pendant le drag ;
- point de `pointerup` ;
- création actuelle de `MoveCommand` ;
- appels directs à `updateComponentPositions` ;
- toute autre écriture persistante de la position ;
- interaction avec la sélection multiple ;
- interaction avec les wires et leur géométrie.

### F.2 Sélection multiple

Si le comportement actuel permet de déplacer plusieurs composants dans une même session, le contrat doit préserver ce comportement fonctionnel.

Cependant, le Handler `MoveComponentHandler` existant est contractuellement un Handler mono-composant. L'implémentation **ne doit pas inventer une nouvelle sémantique multi-composants** dans ce ticket.

Avant implémentation, l'agent doit donc déterminer factuellement comment le drag multi-sélection est actuellement historisé et si le contrat Core existant permet de le représenter sans extension architecturale.

**Si le déplacement multi-sélection exige une nouvelle commande ou un nouveau contrat Core, l'agent doit s'arrêter et remonter le blocage au CSA.**

Il est interdit de contourner cette règle en envoyant plusieurs commandes artificiellement sans validation du comportement Undo/Redo attendu.

### F.3 Document / modèle

La mutation doit préserver toutes les propriétés existantes du composant et modifier uniquement sa position conformément au Handler Core.

Elle ne doit pas :

- modifier `uid` / identité du composant ;
- modifier les pins ;
- modifier les wires topologiques ;
- modifier les waypoints des wires ;
- modifier l'état de simulation ;
- supprimer ou recréer un composant pour simuler un déplacement.

### F.4 Géométrie des wires

Après déplacement, les wires connectés doivent continuer à se recalculer comme aujourd'hui.

Le ticket n'autorise aucune refonte de `buildWirePath()` ou `buildWirePaths()`.

La présence de waypoints persistants doit être préservée. Un déplacement de composant ne doit ni effacer ni réordonner les waypoints d'un wire.

### F.5 Validation

La commande doit passer par le `ValidationEngine` déjà branché au `CommandBus`.

Le Handler existant doit continuer à rejeter :

- un composant inexistant ;
- une position non objet ;
- une position sans coordonnées numériques valides.

Toute amélioration de validation supplémentaire sort du périmètre sauf si elle est déjà imposée par un contrat Core existant.

---

## G. HISTORY / UNDO / REDO

Le ticket réutilise exclusivement la pile historique existante.

Après migration :

1. `MOVE_COMPONENT` doit apparaître dans la même pile Undo/Redo que les mutations CF3 déjà migrées ;
2. Undo doit restaurer exactement la position précédente ;
3. Redo doit réappliquer exactement la position suivante ;
4. une nouvelle mutation après Undo doit invalider le Redo conformément au contrat History existant ;
5. aucune deuxième pile d'historisation ne doit être créée ;
6. le chemin legacy ne doit pas enregistrer une deuxième entrée pour le même déplacement.

### Invariant critique

Un seul déplacement utilisateur ne doit jamais produire deux actions historiques concurrentes : une entrée CF3 et une entrée `MoveCommand` legacy.

---

## H. COMPATIBILITÉ AVEC MB-004.7

MB-004.7 avait pour objectif d'historiser le déplacement via `MoveCommand` et de réactiver le test d'invalidation du Redo.

Le présent ticket **ne doit pas casser les garanties fonctionnelles obtenues par MB-004.7**.

La migration vers CF3 peut remplacer le mécanisme technique de persistance du déplacement, mais elle ne peut pas réintroduire une régression sur :

- Undo ;
- Redo ;
- invalidation du Redo après nouvelle action ;
- déplacement effectif ;
- déplacement avec sélection concernée ;
- conservation du Document.

Si un test MB-004.7 devient obsolète uniquement parce que le canal de mutation change, le remplacement doit être documenté explicitement et le nouveau test doit démontrer la même garantie comportementale.

- application au Document ;
- Undo ;

Vérifier :

- déplacement simple ;
- aucun dispatch pendant `pointermove` ;
- un seul dispatch au `pointerup` ;

- `UPDATE_WIRE_WAYPOINTS`.
